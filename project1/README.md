# 1차 프로젝트 — 탈탈

> 냉장고를 탈탈 털어드립니다

- 서비스: https://taltal.vercel.app
- 레포: https://github.com/uyeon0/taltal
- 기간: 2026-10-28 ~ 11-03 (11/3 발표), 개인 프로젝트

산 재료를 여러 요리에 나눠 쓰는 요리 묶음을 추천하는 서비스다. 화면과 추천 로직은 레포 README에 있고, 여기에는 만든 과정과 결과를 적었다.

## 문제 정의

설문 35건 중 요리하는 31명 가운데 23명(74%)이 최근 한 달 안에 재료를 버렸다. 주로 버리는 재료는 대파, 쌈채소, 숙주처럼 빨리 상하는 채소였다.

같은 재료 묶음을 기존 냉장고 털기 앱 5개에 넣어 보니, 모두 레시피를 한 개씩 추천하고 재료가 얼마나 남는지는 보여 주지 않았다. 그래서 문제를 "며칠에 걸쳐 나눠 쓸 계획이 없다"로 잡았다. 처음에는 "추가 구매가 반복된다"에서 출발해 "재료가 버려진다"를 거쳐 여기까지 좁혀졌다.

## 결과

테스트 장바구니 20개로 "레시피 한 개씩 추천"과 비교했다.

| 지표 | 탈탈 | 한 개씩 추천 |
|---|---|---|
| 남는 재료 비율 (무게 기준) | 61.1% | 70.3% |
| 빨리 상하는 재료의 남는 비율 | 33.2% | 47.8% |
| 가진 양을 넘겨 쓰는 바구니 | 0개 | 18개 |
| 추가로 사는 재료 | 평균 3.0가지 | 평균 4.0가지 |

- 추천 기준을 세 번 바꿨다. "남는 무게 합이 가장 적은 묶음"이 숫자는 가장 좋았지만 상추·숙주를 하나도 쓰지 않는 묶음이 나왔다. 버려지는 건 대부분 빨리 상하는 채소였으므로, 숫자를 조금 내주고 보관 기간 가중치를 주는 기준을 골랐다.
- 탈탈이 더 남긴 바구니 5개는 모두 한 개씩 추천이 재료를 5~7가지 더 산 경우였다. 탈탈은 추가 구매를 3가지로 제한한다.
- 한계: 재료의 g 환산은 AI 추정치이고, "한 개씩 추천"은 실제 경쟁 앱이 아니라 그 방식을 흉내 낸 것이다.

## AI와 일한 방식

- **세션을 역할별로 나눴다.** 날마다 총괄 세션이 할 일을 데이터·로직, 앱·화면 같은 레인으로 나누고, 레인마다 git worktree를 하나씩 줬다. 레인끼리는 서로의 파일을 고치지 않고, 데이터 형식 같은 약속은 문서로 맞췄다.
- **요구사항 → 스펙 → 구현 순서를 지켰다.** 요구사항 문서 5개에서 구현 스펙 14개를 쓰고, 스펙을 확인받은 뒤 구현했다. 문서끼리 어긋나거나 문서에 없는 판단이 필요하면 AI가 고르지 않고 나에게 묻게 했다. 결과는 PR 17개, 테스트 214개다.
- **규칙과 AI를 섞어 썼다.** 레시피 재료명 745개를 장보기 단위로 묶을 때, 규칙 스크립트(v1)와 AI가 하나씩 판단하는 방식(v2)을 정답셋 150개로 비교했다. 자주 쓰는 재료는 규칙으로 충분했고 드문 이름은 AI가 더 잘 묶었다. 다만 AI 결과에도 틀린 것(차조→조 등)이 섞여 있어서, 117개를 하나씩 확인해 맞는 99개만 규칙에 더했다.
- **AI 실수를 기록했다.** 예를 들어 정규화 규칙이 생강즙을 "강즙"으로, 물엿을 "물"로 바꿨는데, 정답셋을 채점하다 찾아 고쳤다.

## 받은 피드백

- **잘한 점**: 한 개씩 추천과 비교한 정량 평가, 추천 기준을 바꾸며 내준 것을 숫자로 설명한 점
- **고칠 점**
  - 레시피 데이터가 비공개라 레포만 받아서는 추천을 돌려 볼 수 없다. 샘플 데이터를 넣어 README만 보고도 재현되게 한다.
  - 장바구니 시나리오 비교만 했고 실제 사용자 테스트는 하지 않았다. 사용자 테스트로 효과를 확인한다.
- 발표는 실제 UI로 만든 발표 자료가 좋은 평가를 받았다.

## 회고

지금까지 개인 프로젝트로는 내가 만들고 싶은 것만 만들었고, 혼자서 문제 정의부터 개발까지 해 본 건 이번이 처음이었다. AI와 함께라면 어떻게든 할 수 있을 거라 생각했는데, 할 일이 생각보다 너무 많아서 결심했던 만큼 꼼꼼하게 진행하지 못했다. 나름 개발자인데 코드 검수를 거의 못 한 게 가장 아쉽다.

에이전트는 반복적인 일에만 직접 정의해서 쓰는 게 좋다고 생각해서 이번에는 거의 쓰지 않았다. 그런데 다른 분들의 발표와 개발 이야기를 들어 보니, 세션 안에서 코드 작업을 작게 쪼개 자연어로 에이전트에게 맡기는 방법도 있었다. 세션을 레인별로 나눠 작업할 때도 코드 작업 때문인지 context가 너무 빨리 차서 고민이었는데, 작은 단위로 쪼개 세션에서 바로 에이전트를 만들어 맡기면 병렬로 작업할 수 있고 세션 사이를 오가는 어지러움도 줄어들 것 같다.
