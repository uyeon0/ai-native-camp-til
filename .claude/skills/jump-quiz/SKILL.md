# 점프 투 파이썬 문제집 만들기

`python-study/quiz/sessions/NN/content.js`만 새로 쓴다. `template.html`은 사용자가 요청할 때만 고친다. 형식과 난이도 기준은 `python-study/quiz/sessions/01/content.js`다.

## 순서

1. **입력 확인.** 회차 번호, 교재 범위(장·절), 블로그 노트 경로를 인자로 받는다. 빠진 것이 있으면 묻고, 추측하지 않는다.
2. **자료 읽기.**
   - 인자로 받은 블로그 노트를 처음부터 끝까지 읽는다.
   - 교재 해당 절(https://wikidocs.net/book/1)을 읽고, 블로그 노트의 각 내용이 교재에 있는지 구분한다. 교재 사이트는 curl과 WebFetch를 막으므로(403) `superset:browser` 스킬로 브라우저 pane에서 연다. 기억에 기대어 구분하지 않는다.
3. **단원 나누기.** 교재 절마다 단원 하나로 나눈다. 단원 하나가 문제 묶음 하나가 된다.
4. **`content.js` 쓰기.** 아래 노트·펼침·문제 규칙을 따른다. 결과 파일 이름에 쓰이는 `range`(예: `"ch03"`, `"ch01-02"`)를 꼭 넣는다.
5. **검증.** `python3 -I`로 실행한다.
   - 문제 코드 전부: 정답 보기가 실행 결과와 같고, 오답 보기 중에 실행 결과와 같은 것이 없어야 한다.
   - 노트 코드 블록 전부: 의도한 에러 말고는 에러가 없어야 하고, `# 결과` 주석이 실제 출력과 같아야 한다.
6. **정답 위치 섞기.** 정답 번호가 고르게 나뉘도록 보기 순서를 바꾼다. 바꾼 뒤 5를 다시 한다.
7. **빌드.** `python3 python-study/quiz/build.py python-study/quiz/sessions/NN/content.js`
8. **화면 확인.** 방법은 `python-study/quiz/CLAUDE.md`의 "확인"을 따른다.
9. **보고.** 결과 파일 경로, 단원별 문제 수, 확인하지 못한 것을 알린다. 커밋은 요청받았을 때만 한다.

## 노트 쓰기

- 블로그 노트의 내용은 하나도 빠뜨리지 않는다. 문장은 문제집에 맞게 다시 써도 된다(실행되는 코드, 질문형 펼침, 시각화, 문제와의 연결). 이미지는 넣지 않는다.
- 교재에 있는 내용은 본문에 둔다. 교재에 없고 사용자가 따로 찾아본 내용(예: "엄밀히 말하면", 공식 문서 인용, 다른 언어와의 비교)은 질문형 펼침으로 접는다.
- 비유를 쓰지 않는다. "쉽게 말하면" 같은 박스도 넣지 않는다.
- 본문은 `~다`체로 쓴다.
- 제목은 `h3`까지만 쓴다(단원 제목이 h2). 더 나눠야 하면 `<p class="lead"><b>머리말</b></p>`로 쓴다.
- 쓸 수 있는 태그: `h3`, `p.lead`, `p`, `ul`, `ol`, `table`, `blockquote`, `a`, `code`, `mark`, `pre.code`, `div.viz`, `details.deep`.
- 코드 블록:
  - `print(...)  # 결과` 형태로 써서 바로 실행되게 한다.
  - `>>>` 형태는 대화형 모드를 설명하는 곳에만 쓴다.
  - 에러를 보여 주는 줄은 블록의 마지막 줄에 두고 `# 에러 이름: 메시지`를 붙인다.
  - 실행할 수 없는 출력 예시는 `<pre class="code norun">`으로 쓴다.
- `<mark>`(라임 형광펜)는 단원마다 1~3개. 형광펜만 이어 읽어도 그 단원의 요약이 되고 문제를 푸는 데 필요한 규칙에 쓴다. 조각이 아니라 앞뒤 문장 없이도 뜻이 통하는 문장 하나 단위로 칠한다.
- 코드만으로 보기 어려운 것(이름과 값의 관계, 인덱스, 흐름)은 인라인 SVG로 그린다. 색은 검정 선과 `var(--hl)`만 쓴다.
- 노트에 문제를 섞지 않는다.

## 질문형 펼침

- 노트: `<details class="deep"><summary>질문</summary>내용</details>`. 관련 본문 바로 아래에 둔다.
- 해설: 문제에 `more: { q: "질문", a: "답 HTML" }`. 문제마다 최대 1개.
- 제목은 그 내용이 답하는 질문으로 쓴다. 예: "a[:]는 안쪽 리스트까지 복사할까?"
- "더 깊게", "심화", "개발자용", "한 걸음 더" 같은 꼬리표를 쓰지 않는다.
- 펼친 내용 안에는 `<mark>`를 쓰지 않는다.

## 문제 쓰기

- 한 회차에 30문제 안팎을 낸다. 기본/심화를 나누지 않는다.
- 단원 순서대로 적는다. 묶음 안에서는 노트만 읽고 풀 수 있는 문제에서 시작해 함정이 있는 문제로 끝낸다.
- 객관식 3~4지선다로, 코드를 읽고 답하는 문제를 낸다.
- 질문은 `~할까?` 말투로 쓴다. 출력을 묻는 문제는 "실행하면 무엇이 출력될까?"로 통일하고, 다른 걸 묻는 문제는 그에 맞게 쓴다(예: "오류가 나는 줄은 어디일까?", "빈칸에 들어갈 것은 무엇일까?"). "출력은?"처럼 명사로 끝내지 않는다.
- 질문에 함정을 드러내는 말("a를 바꾼 뒤" 등)을 넣지 않는다.
- 질문형 펼침에 있는 내용으로는 문제를 몰아서 내지 않는다. 30문제 중 두세 개까지만 낸다.
- 보기만 보고 답을 추론할 수 없게 만든다.
  - 오답은 모두 실제로 할 법한 착각에서 만든다(예: 복사와 참조, 슬라이싱 끝 번호, 정수와 실수, 인덱스를 1부터 세기). 오답마다 어떤 착각인지 설명할 수 있어야 한다.
  - "오류"는 오류라고 착각할 이유가 있을 때만 보기에 넣는다. 빈자리 채우기로 쓰지 않는다.
  - 보기끼리 형식과 길이를 맞춘다. 길이, 자료형 표기, 문장/값 형태만 보고 고를 수 없어야 한다.
  - 그럴듯한 오답이 두 개가 안 나오면 억지로 채우지 않고 2지선다로 낸다.
- `input()`이나 `sys.argv`를 쓰는 코드는 문제에 넣는 입력값·인수를 문제 본문에 적는다(예: "입력으로 `철수`를 넣었다"). 실행기의 입력 칸과 인수 칸에 그 값을 적어 실행할 수 있다.
- `explain`은 코드를 실행 순서대로 따라가며 2~4문장으로 쓴다. 중간 값(변수가 어떻게 바뀌는지, 어떤 조건이 참/거짓인지)을 짧게 보여 주고, 비개발자도 단계를 건너뛰지 않고 따라올 수 있게 한다. 정답 번호와 판정 문구("맞았어요", "틀렸어요")는 쓰지 않는다.
- 그림이 도움이 되는 문제에만 `viz`를 넣는다.
