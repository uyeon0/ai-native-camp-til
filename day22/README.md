# Day 22 — RAG로 문서 근거 챗봇 만들기

## 수업

### 채점 기준은 만들기 전에 정한다

- 질문마다 기대 답과 "꼭 들어갈 말"을 먼저 적는다. 예: 3일 전 취소 환불은 `100% / 3일`, 강사 사정 취소는 `100% / 3,000`
- 문서에 없는 질문도 넣고 "찾지 못했다"고 답해야 맞은 것으로 한다.
- 기준을 답보다 먼저 정해야 답을 본 뒤에 기준이 바뀌지 않는다.

### 조각 크기는 문서 구조에 맞춘다

같은 문서를 세 크기로 잘라 비교했다(겹침은 크기의 10%).

- 100자 · 83개: 표의 한 줄과 그 아래 조건 문장이 다른 조각으로 갈라진다.
- 400자 · 21개: `##` 절 하나(표 + 조건)가 한 조각에 들어간다.
- 1500자 · 6개: 문서 하나가 한 조각이 되어 여러 주제가 섞인다.

문서가 "`##` 절 하나에 주제 하나" 구조라 400자 · 겹침 40자를 썼다.

### "찾지 못했다"는 답은 검색 순위부터 확인한다

- **증상**: 문서에 있는 내용을 물었는데 "문서에서 찾지 못했어요"라고 답했다. 질문 10개 중 1개(9/10).
- **원인**: 정답 조각이 검색 4위였다. 상위 3개만 프롬프트에 들어가므로 LLM은 받은 자료대로 답했다. 환각이 아니라 검색 실패다.
  - 질문의 단어("모아도", "얼마나 자주")와 문서의 단어("자동 수집", "1초에 1번")가 달랐다.
  - "모든 문서 머리말에 회사 이름이 있어서 머리말 조각이 올라온다"는 가설은 틀렸다. 머리말을 뺀 인덱스에서도 정답 조각은 4위(0.467)였다.
- **해결**: k를 3에서 5로 늘려 10/10이 됐다.
  - 다른 방법은 문서에 사용자 말투의 FAQ 넣기, 검색 전에 질문 다시 쓰기다. 문서가 고정 자료라 k를 골랐다.
  - k를 늘리면 순위는 그대로이고 프롬프트에 넣는 범위만 넓어진다. 모든 질문의 입력 토큰이 늘어난다.

### 단어 포함 여부로 채점하면 틀린 답도 맞는다

- "수업 당일에 못 가게 됐어요. 환불돼요?"의 꼭 들어갈 말은 `환불 / 3시간`이다.
- "환불돼요"라고 틀리게 답해도 두 단어가 다 있어서 맞은 것으로 나온다.
- 자동 채점 옆에 사람 판정 칸을 둔다. 답에 덧붙은 말("작성 시", "1,000포인트부터")도 문서에서 찾아 확인한다.

### 환경 함정

- **`temperature=0`이 400 에러**: 실습 모델(`gpt-6-luna`)은 기본값만 받는다. 값을 넘기지 않으면 같은 질문에도 답 문장이 조금씩 달라진다.
- **같은 파일명인데 KeyError**: zip으로 받은 한글 파일명이 macOS에서 NFD로 풀린다. 코드의 NFC 문자열과 다른 키가 되므로 NFC로 이름을 바꾼다.
- **`conda run`**: 표준 입력을 넘기지 않아 heredoc 스크립트는 아무것도 출력하지 않는다. 출력도 프로세스가 끝날 때까지 모아 두므로, 서버 로그는 환경의 python으로 직접 띄워야 보인다.

## 만든 것

### import reference

[import-reference](https://github.com/uyeon0/import-reference) ([배포](https://import-reference.onrender.com)): 파이썬 언어 레퍼런스(한국어)를 근거로 답하고 답마다 공식 문서의 절을 출처로 붙이는 챗봇이다. 오후 실습 과제(PDF 근거 챗봇)를 파이썬 공부용으로 바꿔 만들었다.

### 원본이 HTML이면 PDF로 바꾸지 않는다

- PDF로 바꾸면 절 구조가 사라지고 출처를 절 링크로 달 수 없다. HTML을 절(`<section>`) 단위로 읽었다(273개 절, 855개 조각).
- 파이썬 최신 문서는 PDF를 더 이상 제공하지 않고, 한국어판은 웹 페이지로만 있다.
- 한글 PDF를 읽어야 한다면 `pypdf`는 띄어쓰기를 잃는다("재료비가따로표시된…"). `pymupdf`는 유지한다.
- 구조는 "업로드할 때 임베딩"이 아니라 "미리 수집해 인덱스로 저장하고, 앱은 불러오기만"이 된다.

수집할 때의 함정:

- **charset 없는 응답**: 장 제목이 "ê°ì"로 깨졌다. 응답 헤더에 charset이 없으면 `requests`는 latin-1로 읽는다. `res.encoding = "utf-8"`로 정한다.
- **제목 없는 조각**: 긴 절을 자르면 절 제목은 첫 조각에만 남는다. for 문의 else 설명이 두 번째 조각에 있어서 "for 문에 else 붙이면?"을 못 찾았다. 모든 조각 앞에 "장 › 절" 제목을 붙인다.

### 기호뿐인 질문은 검색 전에 다시 쓴다

- **증상**: "is 와 == 는 어떻게 달라?"를 못 찾았다.
- **원인**: 기호뿐인 짧은 질문은 문서 문장("아이덴티티 비교")과 벡터가 멀다.
- **해결**: 검색 전에 LLM으로 질문을 다시 쓴다. 기호에 공식 문서의 이름을 붙이고 "그럼 그건?" 같은 후속 질문은 대상을 풀어 쓴다. 질문마다 LLM 호출이 2번이 된다.

### 임베딩 검색은 용어가 그대로 있어도 놓친다

- **증상**: "데코레이터는 어떻게 동작해?"의 정답 조각이 855개 중 92위였다. 질문을 다시 써도 38위였다.
- **원인**: 조각 600자 중 앞부분이 함수 정의 전반을 다뤄서 조각 벡터가 데코레이터보다 함수 정의에 가깝다. 임베딩 검색은 단어 일치가 아니라 뜻의 거리로 순위를 매긴다.
- **해결**: 키워드 검색(BM25)을 더한다.
  - 한글은 두 글자씩 겹쳐 자른다(bigram). "데코레이터는"에 "데코레이터"의 bigram이 모두 들어 있어서 형태소 분석기 없이 조사가 붙은 말도 걸린다.
  - 두 순위를 RRF로만 합치면 한쪽에서만 상위인 조각이 빠진다. 키워드 2위 · 임베딩 92위인 조각의 합산 점수가 양쪽 5~10위 조각보다 낮았다. 각 검색의 상위 3개를 무조건 넣고, 순서만 RRF로 정한다.
- **비교**: 질문 10개, 정답 기준은 답이 들어 있는 조각의 문구(같은 절에 조각이 여러 개라 절 이름으로는 판정하지 않는다).
  - 임베딩만 9/10, 키워드만 8/10, 하이브리드 10/10
  - 다시 쓴 질문이 실행마다 달라 순위가 조금씩 바뀐다. 두세 번 돌려서 비교한다.

### 스트리밍 응답의 에러 처리

- **제너레이터에 씌운 데코레이터는 에러를 잡지 못한다**
  - 원인: 제너레이터는 호출할 때가 아니라 `next()`로 꺼낼 때 실행된다. 에러는 데코레이터가 이미 반환한 뒤에 난다.
  - 해결: 한 조각씩 꺼내는 함수를 감싼다.
- **스트림을 연 뒤에는 상태 코드를 바꿀 수 없다**: 키가 없으면 스트림 전에 401을 보내고 틀린 키는 스트림 안의 에러 이벤트로 보낸다.
- **첫 글자 전까지 화면이 멈춘 것처럼 보인다**: 질문 다시 쓰기에 3초쯤 걸린다. 서버가 단계마다 이벤트를 보내고 화면은 "질문 다듬는 중 → 레퍼런스 찾는 중 → 답 쓰는 중"을 스피너로 보여 준다.
- **중간에 멈추면 OpenAI 요청도 끊긴다**: 브라우저가 `AbortController`로 연결을 끊으면 서버는 다음 글자를 보낼 때 `GeneratorExit`를 받고 답 제너레이터와 OpenAI 스트림을 닫는다. 연결을 끊는 시험으로 서버 로그에서 확인했다.
- 키는 서버에 두지 않는다. 사용자가 화면에서 넣은 키를 요청 헤더로만 받고 저장하지 않는다.

### 화면

- **`font:` 단축 속성은 합자 설정을 되돌린다**: 글꼴(Jetendard)이 `==`를 기호 하나로 그려서 합자를 껐다. `body`에만 걸면 `font:`를 쓴 코드 부분은 다시 합쳐진다. 모든 요소에 건다.
- **인용 번호는 화면에서 다시 매긴다**: LLM은 자료 목록 순서로 인용해서 첫 인용이 `[4]`일 수 있다. 처음 나온 순서대로 1, 2, 3으로 바꾸고 같은 절에서 온 조각은 같은 번호로 묶는다.
- **헤드리스 Chrome 스크린샷은 좁은 폭을 정확히 재지 못한다**: 390px로 찍으면 오른쪽이 잘려 보였다. Chrome 창은 일정 폭 아래로 줄어들지 않아 더 넓게 그린 화면을 잘라 찍는다. 모바일 폭은 Playwright 뷰포트로 측정한다. 실제 문제는 머리말과 입력 영역이 화면 대부분을 차지하는 것이었고 좁은 화면에서는 페이지 전체를 스크롤하고 입력줄만 아래에 고정했다.

## AI와 일한 방식

- **처음 보는 개념은 내 말로 정리하고 AI는 검토만 맡긴다**
  - 고칠 곳은 한 번에 하나씩 반영한다.
  - 비유나 모호한 표현은 무엇을 가리키는지 되물어 정확한 말로 바꾼다.
  - AI가 아직 정리하지 않은 개념을 전제로 설명하거나, 앞에서 하지 않은 말을 했다고 하면 바로 정정한다.
- **고치기 전에 원인을 측정한다**: 머리말 가설, 데코레이터 92위, 모바일 잘림 모두 수정 전에 순위와 크기를 먼저 확인했다. 세 번 중 두 번은 처음 생각한 원인이 아니었다.
